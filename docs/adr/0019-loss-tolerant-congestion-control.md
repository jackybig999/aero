# ADR-0019 拥塞控制：对随机丢包不敏感的发送方（quic-go fork）

状态：accepted（2026-11-25，用户决定：先做方案 B 再用方案 A 取代）
关系：细化 ADR-0017（双传输 CONNECT-IP）的 P5“丢包测量”；不改变会话与传输方式的设计

## 背景
真机现象：连接成功后网页极慢、下载几乎没有进展、AI 对话与 AI 命令行工具启动不了。逐项排除后（见下）定位到隧道的 QUIC 拥塞控制。

已排除（均有实测）：路由下发耗时（9887 条 0.79 秒）；启动耗时（`[START]` 合计 2.5~2.8 秒）；客户端本机 UDP 缓冲区与网卡丢包（`netstat -s -p udp` 接收错误 0、网卡丢弃 0）；
服务端限速（`-bw-user` 默认 0）；服务端 UDP 缓冲区（`ss` 显示 14 MB，`UdpRcvbufErrors` 0）；复用层静默丢包（队列满时阻塞反压）。
真机对照：经 TUN（IP 数据报）与经本地代理（QUIC 流）几乎一样慢（56.8 与 50.8 KB/s），说明瓶颈在两者共有的 QUIC 连接。

本地复现（`tests/e2e`，隔离命名空间，`tc netem`，两端各注入一半，往返 190ms）：

| 条件 | 吞吐 |
|---|---|
| 无延迟无丢包 | 3.8 Gbit/s |
| 仅延迟 | 156 Mbit/s |
| 每方向 0.1% 丢包 | 3~5 Mbit/s |
| 每方向 0.5% 丢包 | 1.9 Mbit/s |
| 同上，发送方忽略随机丢包（实验副本） | 97~128 Mbit/s |

根因：quic-go v0.63.0 的拥塞控制只有一种基于丢包的实现（`internal/congestion`，创建时写的是 `true, // use Reno`，即 NewReno：丢包乘 0.7，拥塞避免期每个往返只加一个包），没有对外的替换接口。随机丢包的长距离链路上窗口既被反复压低，又因为每个往返只涨一个包而恢复极慢（往返 190ms 时恢复一次要几百个往返）。
DATAGRAM 帧同样受拥塞控制约束：RFC 9221 §5.4 “DATAGRAM frames employ the QUIC connection's congestion controller”，§5.2 它们是 ack-eliciting；quic-go 里 ack-eliciting 的包增加 `bytesInFlight` 并调用 `congestion.OnPacketSent`（`internal/ackhandler/sent_packet_handler.go:285-300`）。所以 IP 数据报同样受限。TCP 在其上还有第二层拥塞控制（RFC 9484 §10），丢包被两层放大。

## 备选
A. BBR 发送方：按带宽与时延模型发送，不把随机丢包当拥塞。业界标准做法；工作量最大，需带宽瓶颈测试验证公平性与不过冲。
B. “lossy” 发送方：CUBIC 增长曲线（按时间增长，与往返时延无关）加选择性的丢包响应——最近丢包率低于 5% 且平滑 RTT 没有明显高于最小 RTT（没有在排队）时，把丢包当作随机丢包，不降窗口；否则按原行为降窗口。经验规则，真拥塞时不如 BBR 稳。
C. Brutal（固定速率）：按订阅里的带宽固定速率发送，不理丢包。最简单；需要每用户配带宽，配高了会塞满自己的出口线路。
D. 不改拥塞控制，改为终结 TCP 后经 QUIC 流转发：违反 ADR-0012 第 1 条（禁止用户态协议栈）与既定“永不用 gVisor”，排除。

## 决定
先做 B，再用 A 取代 B（用户 2026-11-25 决定）。不做 C 与 D。

1. **fork quic-go**：`third_party/quic-go`（上游 v0.63.0，MIT，保持原 LICENSE），主模块 `replace` 引入；目录里的 `FORK.md` 登记全部改动；CI 增加一步运行被改动的包与全量 vet。
2. **配置开关**：`quic.Config` 增加 `CongestionControl` 字段（`""`/`"cubic"` 为上游行为；`"lossy"` 为方案 B；方案 A 落地后增加 `"bbr"`）。客户端与服务端都从自己的配置/环境变量选择，**任何一端都可以随时回退到 `cubic`**。
3. **两端都要换**：下行（下载）由服务端发送，上行由客户端发送。只升级节点即可改善所有客户端的下载，这是部署上的好处。
4. **验证**：`tests/e2e` 的 netem 矩阵（延迟、延迟加丢包、带宽瓶颈 `tbf`、瓶颈加随机丢包）；单元测试覆盖“随机丢包不降窗口”“RTT 膨胀或高丢包率时仍降窗口”“持续拥塞不失控”。
5. **不扩大宿主修改**：不改 sysctl、不改防火墙；只改进程内的发送算法。

## 后果
- 好处：长距离随机丢包链路上吞吐从 1~5 Mbit/s 回到接近链路容量；网页、下载、AI 的 TLS 握手与长连接恢复正常。
- 风险：忽略丢包的发送方在真正拥塞的共享链路上可能不够友好，所以方案 B 保留 RTT 膨胀与高丢包率两个信号，仍会降窗口；方案 A 取代后用带宽瓶颈测试验证。
- 维护面：多一个 quic-go fork，升级上游时要重放 `FORK.md` 表里的改动。
- 与 ADR-0017 P5 的关系：本 ADR 的矩阵给出了丢包对吞吐的量化数据；是否让普通 TCP 也走可靠通道（R）仍待 P5 的真机丢包测量。
